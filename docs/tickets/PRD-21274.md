## Requirement understanding

One line: Review backup and disaster-recovery infrastructure status via Slide.

Agent Platform wants to let an agent/user ask about the health of an MSP's Slide backup and
disaster-recovery (BCDR) estate — which clients, agents and devices are protected, whether
recent backups succeeded, whether recovery points pass integrity verification, and what active
alerts need attention — without a human opening the Slide console. The ticket links to the
Slide tile on `conduit.wyre.ai` (a generic connector-catalog placeholder, not a spec) and
carries no further scoping beyond the title and the one-line ask; this is a "build the
connector from the vendor's public API" ticket, not a request for a named missing tool (see
`references/mcp-track.md` 2.1, row "not found -> onboard a new product").

## Product design

### Goals / Non-goals

Goals (v1):
- Expose Slide's BCDR status data to the Agent Platform as read-only MCP tools: which clients/
  sites are onboarded, which agents (protected systems) and devices (Slide appliances) exist
  and whether they are checking in, whether recent backups ran and succeeded, whether the
  latest recovery points (snapshots) pass Slide's own integrity verification, and which alerts
  are open.
- Every tool call is scoped to the Slide API key supplied on that request's own Header — no
  shared credential, no cross-request state (standard MCP contract, not special to Slide).

Non-goals (v1):
- No write or destructive operations: no starting backups, no creating/deleting restores
  (file, image, virtual-machine), no managing networks/VLANs/IPsec/port-forwards/WireGuard
  peers, no pairing new agents, no device power control, no billing document retrieval. The
  ask is "review ... status"; none of the above is a status read. See "Decisions made by
  DEV01" for the full include/exclude list and how to extend it later.
- No UI — this ticket delivers a backend MCP connector consumed by agents, not an
  Agent-Platform-facing page.
- No change to any other repo; this is a brand-new, self-contained MCP service.

### Acceptance criteria

- AC1: Given a valid Slide API key on the request, when the agent asks for the list of Slide
  clients (the MSP's end-customers/sites in Slide), then it receives each client's id and
  name, with no more than `limit` (default 10, max 50) returned per call and a signal when
  more exist.
- AC2: Given a client id, when the agent asks for that client's protected systems (agents),
  then it receives each agent's id, display name, hostname, platform, last-seen timestamp, and
  whether its backup schedule is active or paused — enough to say "this system is/is not being
  backed up right now."
- AC3: Given an agent or device id, when the agent asks for recent backup runs, then it
  receives each run's start/end time, status, and (if failed) an error code/message — enough
  to say "did yesterday's backup succeed."
- AC4: Given a device id (a physical/virtual Slide appliance), when the agent asks for that
  device's status, then it receives its service status, last-seen timestamp, and storage
  used/total — enough to say "is the on-prem/cloud appliance itself healthy and not full."
- AC5: Given no filter, when the agent asks for alerts, then it receives open (unresolved)
  alerts with type and creation time by default, and can also ask for resolved ones — enough
  to say "what needs attention right now."
- AC6: Given a snapshot (recovery point) id, when the agent asks for its verification status,
  then it receives the boot-verification, filesystem-verification and service-verification
  results — enough to say "if we had to recover from this point, would it actually come up."
- AC7: Given a request with no Slide credential Header, when any tool is called, then the
  response is a structured `unauthorized`-shaped 401 naming the required Header, not a crash
  or a silent empty result.
- AC8: Given a Slide API key that Slide itself rejects, when any tool is called, then the
  response is a structured `unauthorized` error whose message does not echo the Header value
  or the raw vendor response body back to the caller.
- AC9: Given a list call, when more results exist than one page, then the response says so
  (a `has_more`-style signal) rather than silently truncating or trying to return everything.
- AC10: Given Slide's API is unreachable, rate-limiting, or returns a 5xx, when a tool is
  called, then the response is a structured `upstream_error` or `rate_limited` error marked
  `retryable: true`, not a request that hangs past the 120s budget or an unhandled exception.
- AC11: Given two concurrent requests carrying two different clients' Slide API keys, when
  both call the same tool at the same time, then each response reflects only its own caller's
  key and data — no credential or result ever crosses between the two requests.

### Open questions

- [non-blocking] Should restore-related status (e.g., "is a restore currently running") be visible
  in v1 even though triggering a restore is out of scope? — Assumed: no, deferred to a
  follow-up once there is a concrete ask for it (`Restores (File/Image/Virt)` are listed but
  not read in v1; see Decisions). Not aware of any signal that this blocks acceptance.
- [assumed] Which Slide object maps to "disaster-recovery infrastructure" beyond backups: this
  design treats Snapshot verification (`verify_boot_status` / `verify_fs_status` /
  `verify_service_status`) as the DR-readiness signal, since that is the only
  recovery-oriented health field Slide's API exposes short of actually performing a restore.
  If product later means something more specific (e.g. actual virtualized-instance failover
  status), AC6 and the matching tool need rework.

## Tech design

### Conclusion

Build the first version of `slide-mcp` from scratch per the vendor-mcp-development SOP:
Python 3.12 + uv + FastMCP, Streamable HTTP, stateless, credential read from one request
Header (`X-Slide-Api-Key`) and forwarded to Slide as `Authorization: Bearer <token>`. Expose
12 read-only tools across 7 Slide resource groups (clients, agents, devices, backups,
snapshots, alerts, audit log) that together answer "what is Slide protecting, is it backing
up, and would the recovery points actually work." No write/destructive tool in v1 — Slide's
write surface (pairing agents, managing networks, creating restores, billing) is out of scope
for a "review ... status" ask and is listed as follow-up work, not built speculatively
(YAGNI).

### Data & API contract

MCP side (this service):

- Endpoint: `POST /mcp` (Streamable HTTP, `stateless_http=True`), `GET /health` → `{"status":
  "ok"}` with no upstream call.
- Credential Header: `X-Slide-Api-Key` (required, masked). Missing → 401 body
  `{"error": {"code": "unauthorized", "message": "Missing required header: X-Slide-Api-Key", "retryable": false}}`.
- Tool result envelope (success): the tool's JSON result, compact (`ensure_ascii=False`, no
  `indent`), capped at 20000 chars with truncation + `has_more` when a list would exceed it.
- Tool result envelope (error): `{"error": {"code": "<unauthorized|not_found|invalid_argument|rate_limited|upstream_error|not_configured>", "message": "<human-readable, no credentials or raw vendor body>", "retryable": <bool>}}`.
- Example — `slide_list_backups(agent_id="a_123", limit=20)` success:
  `{"data": [{"backup_id": "b_1", "agent_id": "a_123", "started_at": "2026-11-01T02:00:00Z", "ended_at": "2026-11-01T02:14:00Z", "status": "succeeded", "error_code": null, "error_message": null}], "has_more": false}`
- Example — same call with an expired Slide key:
  `{"error": {"code": "unauthorized", "message": "Slide rejected the API key (401)", "retryable": false}}`

Upstream (Slide) side, called with `Authorization: Bearer <X-Slide-Api-Key value>`:

- `GET https://api.slide.tech/v1/<resource>?limit=&offset=&<filters>` → `{"data": [...], "pagination": {"next_offset"?: int}}`.
- `GET https://api.slide.tech/v1/<resource>/{id}` → the resource object, 404 if absent.
- Error body on 4xx/5xx: `{"codes": [...], "message": "...", "details": [...]}` — logged
  (status code + `codes` only, never `message`/`details` verbatim in case Slide ever echoes
  request content back) and mapped per the vocabulary above.

DB: none — this service holds no state and owns no database.

Backward compatibility: first version of a new connector, nothing to be compatible with yet.
Future tool/parameter changes follow SOP §13 (renames/removals are breaking and must be
announced; new optional params/fields are not).

### Key flow / sequence

1. Agent Platform's gateway calls `POST /mcp` with `X-Slide-Api-Key: <tenant's key>` and a
   `tools/call` request, e.g. `slide_list_backups`.
2. `server.py` middleware reads the Header into a request-scoped `ContextVar`; builds a
   `client_factory` bound to that token and `config.slide_base_url`.
3. The tool handler in `tools/backups.py` calls `api_client.list_backups(**args)`.
4. `api_client.py` sends `GET /v1/backup?limit=&offset=&...` to Slide with
   `Authorization: Bearer <token>`, 5s/30s timeouts, retrying 429/5xx with backoff up to the
   120s total budget.
5. On 2xx: tool trims/shapes the response, returns the JSON string.
   On 4xx/5xx/timeout: `api_client` raises `SlideAPIError`; `errors.py` maps it to the fixed
   envelope; the tool returns that string (never raises past the tool boundary, SOP §4.1).
6. Middleware `finally` resets the `ContextVar` regardless of outcome.

### Non-functional

- Idempotency/concurrency: every tool is a read; no idempotency key needed. Per-request
  `ContextVar` plus a fresh `api_client` per call means two concurrent requests never share a
  token or an HTTP connection's auth state (AC11); no module-level/global credential storage
  anywhere in the codebase (grep-checked in self-test, SOP §3.3/§3.4).
- Performance: Slide's own page cap (max 50) bounds single-call cost; tools default to 10 to
  keep typical responses small; no tool fans out into more than one Slide call (no N+1 joins —
  that composite-rollup idea was deferred, see Option B).
- Security: credential never leaves the request Header → Bearer-header round trip; never
  logged, never placed in config, never in error messages (`errors.py` only forwards Slide's
  HTTP status and `codes`, not the free-text `message`/`details`, to avoid ever relaying
  something Slide might someday echo back from request input). DNS-rebinding protection
  disabled per SOP §7 (service sits behind the gateway, not directly internet-facing).
- Multi-tenant isolation: there is no platform-side tenant table in this service — isolation
  is "one Slide API key per request, never persisted, never shared" (SOP §3), verified by
  `tests/test_middleware.py` (AC11) and a Dockerized self-test running two concurrent requests
  with two different fake keys.
- Observability: structured log per tool call — tool name, resource id/filter summary
  (no credential), Slide path + status code, duration, error code if any (SOP §6).

### Decisions made by DEV01

(no product contact to ask at design time; each is reversible via a follow-up ticket)

- **Scope v1 to read-only status tools; exclude every write/management endpoint** (agent
  pairing, device power/VLAN/network/IPsec/WireGuard management, creating file/image/VM
  restores, billing document retrieval) — why: the ask is literally "review ... status"; SOP
  §2.1 says tools are capabilities the ticket asked for, not an endpoint mirror; shipping
  unrequested destructive tools (delete a network, create a restore) means designing a
  write-gating story nobody asked for. Alternative not chosen: mirror the full 60-path surface
  (Option C above) — rejected as over-building (YAGNI) and a ≤20-tool-guidance violation.
- **12 tools: a `list`/`get` pair for agents, devices, backups, snapshots, and alerts, plus a
  list-only tool for clients and for the audit log (no composite "health rollup" tool)**
  — why: keeps each tool's behavior traceable to one Slide endpoint, easiest to debug and to
  extend later; alternative (Option B, a joined summary tool) deferred until there is a
  concrete ask for what "healthy" should mean, since baking in an opinion now would be a
  guess.
- **Treat Snapshot verification fields (`verify_boot_status`/`verify_fs_status`/
  `verify_service_status`) as the "disaster-recovery" half of the ask, Backup status as the
  "backup" half** — why: these are the only two status-shaped signals Slide's API exposes for
  "did the backup run" and "would the recovery actually work" respectively, without actually
  performing a restore (which is out of scope). Alternative: wait for product to name the
  exact DR signal — not chosen because the mapping is reasonably unambiguous from the schema
  itself (see Open Questions for the one spot this could be wrong).
- **Single credential field, `X-Slide-Api-Key`, forwarded as a Bearer token** — why: Slide's
  entire API uses one `BearerAuth` scheme (confirmed in the OpenAPI spec's
  `securitySchemes`); matches the "variant 1 · credential-only" shape already used by
  comparable single-token backup connectors in the MCP Hub catalog (wiki:
  `ProductDocs/_connector-fields.md § Variant 1`, e.g. Backup Radar's one masked `API Key*`
  field) — not a new pattern. Alternative (splitting base URL into its own field): not needed,
  Slide has one fixed API host, unlike multi-region vendors in that table.
- **List tools default `limit=10`, hard cap `limit=50`** — why: mirrors Slide's own server-side
  cap exactly (`QueryLimit` schema: default 10, maximum 50) rather than inventing a different
  number; a tool can never request more than Slide itself will return in one call.
- **Clients are list-only (no `get client by id` tool)** — why: no AC asks for a single
  client's detail beyond id/name, which `slide_list_clients` already returns per item; adding
  a `slide_get_client` tool with no AC driving it would be speculative (YAGNI). Alternative:
  add it anyway for symmetry with the other resources — rejected, matches the audit-log
  reasoning immediately below.
- **Audit log is read-only and list-only (no `get audit by id` tool)** — why: the per-row
  detail an agent would want (actor, action, resource, time) is already in the list response;
  Slide's `GET /v1/audit/{audit_id}` exists but adds no field the list doesn't have, so a
  second tool for it would be redundant (DRY / token economy, SOP §2.5).
- **Accounts endpoint not exposed as a tool in v1** — why: `GET /v1/account` describes the
  MSP's own Slide account (billing contact, alert emails), not BCDR status of a *client's*
  infrastructure; it doesn't answer "review backup and DR status" and would be the one tool in
  the set that leaks the MSP's own contact/billing info rather than a client's protection
  status. Alternative: include it for a cheap "is the key valid" connectivity check — rejected
  because `slide_list_clients` already serves that purpose without the contact-info exposure.

### Effort & breakdown

Story points: 3
Tier: cross-service, many acceptance scenarios (row "3") — new external integration with 12
tools across 7 resource groups, each needing its own success/error/pagination test coverage
(~14 test cases), even though the vendor API itself is uniform and well-documented.
Considerations: 1 external system (Slide), brand-new build (not a modification); external API
is documented via OpenAPI (reduces the "unknown" factor that usually pushes a new connector to
5); no write/destructive operations in v1 (narrows the surface versus a full-CRUD connector);
no data migration; no UI; security/isolation work is the standard per-request-Header pattern
every MCP ticket carries, not an incremental cost specific to this one; 11 acceptance
scenarios, 7 resource groups, 12 tools.
Main uncertainty: whether Slide's snapshot verification fields behave exactly as the schema
implies on a real tenant (Open Questions, "assumed") — does not change the tool shape, only
whether the field mapping needs a follow-up tweak once a real account is available.
Order inside this ticket: 1) config/api_client/server/errors scaffolding 2) clients + agents +
devices tools (what is protected) 3) backups + snapshots tools (did it work, would it recover)
4) alerts + audit tools (what needs attention) 5) tests + README + container.

### Risks & dependencies

- Risk: Slide's verification fields (`verify_boot_status` etc.) are undocumented beyond the
  OpenAPI schema's field names — no prose description of the possible enum values was found
  in the spec. Mitigation: `api_client`/tools pass the string through as-is rather than
  re-encoding it into an invented enum, so an unexpected value surfaces to the caller instead
  of being silently mapped to the wrong bucket.
- Risk: no Slide test account available to DEV01 at design or build time. Per mcp-track.md
  §2.5/§3, this does not block shipping — unit tests mock the API; the real-account check is
  flagged "needs a real vendor account" and does not gate INT publish.
- Dependency: none on any other ticket or repo — single new repo, `release order: any`.

## Test cases

- TC1 (AC1, auto): `slide_list_clients()` with a valid key returns each client's id/name,
  respecting `limit`/`offset`.
- TC2 (AC2, auto): `slide_list_agents(client_id=...)` returns id, display name, hostname,
  platform, `last_seen_at`, and whether the backup schedule is active/paused for each agent
  under that client.
- TC3 (AC3, auto): `slide_list_backups(agent_id=...)` returns each run's start/end time and
  status; a failed run also carries an error code and message.
- TC4 (AC3, manual, needs a real Slide tenant): on a live account, a backup shown as "failed"
  in the Slide console is also reported as failed (with a matching error) by
  `slide_get_backup`.
- TC5 (AC4, auto): `slide_list_devices()` / `slide_get_device(device_id=...)` return service
  status, last-seen time, and storage used/total for a Slide appliance.
- TC6 (AC5, auto): `slide_list_alerts()` with no filter returns only unresolved alerts by
  default; passing `resolved=true` returns resolved ones instead.
- TC7 (AC5, auto): `slide_list_alerts()` against a client with zero alerts returns an empty
  `data` list, not a `not_found` error.
- TC8 (AC6, auto): `slide_get_snapshot(snapshot_id=...)` returns `verify_boot_status`,
  `verify_fs_status`, and `verify_service_status` for that recovery point.
- TC9 (AC7, auto): any tool called with the `X-Slide-Api-Key` Header absent returns
  `{"error": {"code": "unauthorized", ...}}` naming the Header, not a 500 or an exception.
- TC10 (AC8, auto): any tool called with a key Slide's API rejects (mocked 401) returns a
  structured `unauthorized` error whose `message` does not contain the submitted key or
  Slide's raw response body.
- TC11 (AC9, auto): a `list_*` call against a mocked 51-item result set returns exactly
  `limit` items plus a `has_more`/`next_offset` signal, never the full 51.

  `rate_limited` / `upstream_error` respectively, both with `retryable: true`, and never as an
  unhandled exception or a hang past the test's timeout.

  their own key in the outgoing request to the mocked Slide API — `tests/test_middleware.py`

  `initialize → tools/list → tools/call` pass against a live Slide account from a real MCP
